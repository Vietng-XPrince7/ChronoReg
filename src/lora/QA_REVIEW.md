# UET QA curation for continual LoRA

This workflow belongs to `feature/lora-continual`. It prepares **training** QA for the LoRA model. It does not create the team's official benchmark, infer missing regulation validity, edit shared schemas, or train on unsupervised draft answers.

## Ground truth and boundaries

Source evidence is taken from `data/raw/uet/markdown/`. Document eligibility comes from the version registry generated by `src/versioning`. Only documents with confirmed scope and academic-year metadata, a verified source, and no publication hold are used to propose LoRA training examples.

`as_of_year` means the start of the academic year (`2025` = academic year `2025-2026`), **pending confirmation with Việt**. An academic-year label does not establish that an amendment was in force on every date in that year. For questions involving mid-year amendments or specific dates, require more detailed version evidence; reject ambiguous drafts.

The extraction code is intentionally conservative: it proposes short source passages for review, not fact-perfect question/answer pairs. It may propose procedural preambles, incomplete table headings, long paragraphs or generic questions. These must be edited or rejected. A snippet can exist verbatim while an answer based on it is still legally or temporally wrong.

## How to generate a review batch

From `C:\HaiAnh\ChronoReg-LoRA` in PowerShell, using the repo's installed Python environment (Windows Python for CPU-only data commands or the Ubuntu Python):

```powershell
py -m src.versioning.cli build
py -m src.lora.cli propose
py -m src.lora.cli review-template
```

Expected local, **Git-ignored** files:

- `src/lora/runs/candidates.jsonl`: original source-bound **drafts**; do not edit it after generating the review template.
- `src/lora/runs/review_decisions.jsonl`: a decision record for each draft. Every decision starts as `pending`; no approvals are invented.
- `src/lora/runs/review_coverage.csv`: counts by year. These are **counts of drafts**, not trained/approved QA.

The review-template command refuses to overwrite an existing decisions file, protecting prior manual decisions. If documents or generated candidates change, preserve the old review decisions in a secure local archive and start a new review batch. Never blindly transplant a decision between changed candidate hashes.

Each decision carries `candidate_id`, `candidate_sha256`, immutable `doc_id`, `as_of_year`, `source_file`, and `evidence_quote`, plus writable `decision`, `reviewer`, `reviewed_at`, `review_note`, `question`, `answer`.

Review one row at a time against the original UET source and the latest version registry:

1. Check *year and population/program scope*. A year appearing in a heading, publication date or filename is not evidence of academic-year applicability.
2. Check document authority and relation to later amendments. Hold outdated tariffs, personal scholarship recipient lists, broken tables, directories, or passages that cannot be reliably interpreted.
3. Verify the citation and source passage; edit the **question to ask a concrete fact** (not “mục này quy định gì?”) and write an independently checked, concise answer. A changed answer must still be supported by the exact `evidence_quote` and the broader document scope.
4. For approved rows, set `decision` to `approve`, `reviewer` to a human reviewer name or group alias, `reviewed_at` to `YYYY-MM-DD`, and `review_note` to the substantive reason the QA is valid. To reject, use `reject` with review details. Pending is safe and produces no training data.
5. Never copy names, student IDs, contacts, or other student-level personal data into QA. Never put official benchmark questions/answers into training or use the benchmark to tune the model.

## Finalize the reviewed subset

```powershell
py -m src.lora.cli review-finalize
```

This rechecks all source hashes, the latest document registry, holds, academic year, signed review decisions, and approved QA contract. It fails closed on stale candidates or unsafe documents. It exports **only explicitly human-approved records** into `src/lora/runs/approved_qa.jsonl`.

Without the official held-out benchmark, the command honestly reports `benchmark_overlap_checked: false`. It does **not** authorize training; `prepare` requires the benchmark and approved QA in **every requested year**. Once Việt supplies the separate benchmark file, pass `--benchmark path/to/official_benchmark.jsonl` on a new review batch or run `prepare`; keep development QA separate from that protected evaluation set.

By default, finalization refuses to overwrite an existing approved QA file. To iterate on review decisions, archive the current local output and start a new batch. Do not commit the ignored local `runs/` files.
